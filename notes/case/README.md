# case/：某原理在某场景的一次落地

**放什么**：只对这一次具体场景成立的内容。业务背景、为什么选这个方法、数据怎么整、结果、踩的坑。一次落地一篇。

**不放什么**：原理本身的推导。那些在 `../concept/` 里，这里用 `uses` 指过去，正文用链接引用，**不复制**。

`case` 是整个知识库里最有价值的类型：原理网上到处有，「我在什么场景下怎么用的」只有你有。

## 必填边

`uses: [<concept-id 或 pattern-id>, ...]`，至少一个。这是「Fisher 我用过几次」这类问题的答案来源。没有 uses 的 case 不是 case，先想清楚它用了什么原理；真没有就说明它其实是 `qa` 或者该进 inbox。

## 写作深度：写过程，不是只写结果

case 的价值在"我当时是怎么一步步做的、为什么这么做"，不在最后那个数。标准：**没经历过这件事的人能照着复现**。

- **数据怎么来的**：工具输出原样贴，解释每个数是什么、哪个是分子哪个是分母。
- **数据怎么变成方法要的形状**：每一步转换写出来（正则抓了什么、表怎么摆、参数顺序为什么这样）。
- **每一行关键代码对应原理的哪一步**，链到 concept，不复制推导。
- **数字一步步算**：不要只写"p = 0.031"，写 $n$、$r_1$、$c_1$ 是多少、期望是多少、观测是多少、尾部怎么加起来的。
- **补算要写算法和依据**：用了什么公式、为什么选它而不是更简单的那个。
- **复盘写判断的依据**，不只写结论；"如果重来"给可执行的做法。
- 篇幅不设上限。

`## 怎么做的` 和 `## 结果与复盘` 推荐按"第 1 步 / 第 2 步 …"分小节（`###`）。

## 正文结构（必需标题，lint 会查）

```markdown
## 背景
业务是什么、要回答什么问题、数据长什么样、有什么约束（样本只有 40 个、必须 24h 内出结论）。

## 为什么用它
为什么选这个原理/套路，而不是更常见的那个。「卡方要求期望频数 ≥ 5，这里不满足」。这一节最能体现判断力。

## 怎么做的
数据怎么整成方法要的形状、代码、参数。引用原理用链接：[Fisher 精确检验](../concept/fisher-exact-test.md)。

## 结果与复盘
结论是什么、后来验证对了没、踩了什么坑、下次会怎么做。
```

## 字段

| 字段 | 说明 |
|---|---|
| `uses` | 必填。用到的 concept / pattern |
| `related` | 相似的其他 case，或引申出的 qa |
| `tags` | 打业务标签（`ab-test` / `risk-control`）+ 领域标签（`statistics`） |

## id 命名

`<场景>-<方法>`：`ab-test-small-sample-fisher`、`risk-feature-significance-fisher`。看 id 就知道是哪个场景用了什么。

## 什么时候该提炼 pattern

同一个原理出现在 ≥ 2 篇 case 里，而且做法相似，就在 `../pattern/` 写一篇「小样本二分类显著性」这种套路，两篇 case 的 `uses` 加上它。
